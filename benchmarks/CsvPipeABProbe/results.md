# End-to-End PipeReader A/B Evidence (September 2026)

## Scope and Provenance

The initial experiment compares pre-decoder-change `626f8af` with merged PR #127,
`8309abf`. No parser or generator production changes were made for the initial probe.
It measures complete reads, including creation, header handling, consumption,
validation and disposal, excluding fixture generation. See [method](README.md).

Machine: AMD Ryzen AI 9 HX PRO 370, Windows build 26220, .NET 10.0.12, workstation
GC, 24 logical processors. Final paired runs used CPU affinity mask `10`, 2000
data rows, 20 measured pairs, six warmup pairs, and a 50 ms calibration target.
Calibration follows eight untimed reads per side and doubles a shared batch
size until the faster side meets the target, capped at 1000 reads. Changing
machine load can still shorten later measured batches; the target is not a
guarantee of steady-state sample duration.

Captured logs are retained locally under `BenchmarkDotNet.Artifacts`:

- `pipe-e2e-verify.ndjson`: 37-row full correctness preflight.
- `pipe-e2e-ab-final-1.ndjson`: full matrix, with 27 timed cases and nine invalid
  generated cases; exit code 1 is the deliberate correctness-gate failure.
- `pipe-e2e-ab-final-2.ndjson`: repeat of all 12 Decode cases; exit code 0.
- `pipe-e2e-aa-plain.ndjson`: same-source `8309abf` A/A, all nine Plain cases;
  exit code 0. This is not a full-matrix correctness pass.

The A/B baseline module ID was `928be182-0351-4e25-8644-93c71b7257f9` and candidate
module ID `2cc35513-2906-4056-b905-cd4c8dd38849`. The A/A baseline was independently
rebuilt from `8309abf` under the distinct baseline assembly name; its module ID was
`1d4cbc2f-a16e-4b16-bc96-4c410c02f9cf`. Each log records loaded parser/model module
IDs, source labels, every pair, and calibration.
Earlier exploratory runs preceded the warm-before-calibration fix and are not
used for timing conclusions.

## Initial Correctness Blocker

All 12 Scan controls passed row/column counts. All 12 Decode cases and three
Plain Generated cases passed the independent input-derived content checksum.
The remaining nine Generated cases with quoted/escaped notes failed on both
source revisions.
Neither side is timed in those cases, even though their wrong checksums match.

Minimal logical example: a Note containing `said "hello", row 1` is serialized as
`"said ""hello"", row 1"`. The generated byte string binder calls
`Encoding.UTF8.GetString` on the raw column span rather than performing CSV
unquoting/unescaping. Borrowed column decoding returns the original logical text;
generated binding retains CSV quoting. This is an existing semantic discrepancy,
not a regression from PR #127.

Fix and regression-test generated binding's quoting semantics before assessing
typed throughput on escaped workloads. Tests should include custom quotes,
escape characters, quotes-disabled options and segmented input, not just this
default-quote fixture. The full probe intentionally remains a failing gate until
both compared implementations produce equivalent logical records.

## Timing Is Not Release-Quality Evidence

A CPU-load snapshot during the experiment was 91%. The probe's one-CPU affinity
does not isolate it from other processes. We did not stop unrelated processes or
change the machine's persistent configuration.

The same-source Plain A/A control exposed substantial timing variation:

| Transport | Path | Median Ratio | p10 | p90 |
|---|---|---:|---:|---:|
| Contiguous | Scan | 1.00 | 0.48 | 1.53 |
| Contiguous | Decode | 1.14 | 0.56 | 1.60 |
| Contiguous | Generated | 0.95 | 0.72 | 1.31 |
| Segmented128 | Scan | 0.98 | 0.75 | 1.31 |
| Segmented128 | Decode | 1.09 | 0.64 | 1.85 |
| Segmented128 | Generated | 1.04 | 0.64 | 1.50 |
| Stream4096 | Scan | 1.04 | 0.63 | 1.65 |
| Stream4096 | Decode | 1.28 | 0.31 | 1.95 |
| Stream4096 | Generated | 0.97 | 0.75 | 2.10 |

Even repeated A/B timing directions changed: Plain segmented Decode's median
ratio was about 0.79 in the first run and 1.47 in the second. Unicode stream
Decode moved from about 0.79 to 0.99. Such results do not establish a precise
speedup, regression, or an optimization ranking.

**Decision:** address the generated-binding correctness discrepancy first. Then
repeat the checked A/B and same-source A/A on an idle machine or dedicated runner,
with the same runtime/GC/affinity settings. Require stable controls and consistent
repeats before choosing between segmented-copy/scanning and typed-binding work.
Do not attribute the synthetic transport gap entirely to copying: segmentation
also changes scanner/batch paths. Do not use Scan-versus-Generated ratios as
equivalent-work comparisons.

### Workload-Thread Attribution

The all-thread `topN` reports are not usable as workload CPU percentages. For
example, a contiguous capture attributed about half its global report to an
initialization thread whose converted timeline lasted only about 13-15 ms,
while the reading thread spanned approximately 30 seconds. Filtering by a
method name in that global report would not repair its denominator.

The following descriptive shares were calculated from each evented Speedscope
timeline separately. Positive intervals between consecutive events were assigned
to the active stack; inclusive attribution counted each frame once per interval,
and exclusive attribution used the leaf method beneath the synthetic `CPU_TIME`
marker. Open/close frames were checked for balance. The selected thread executed
the checked `Case.BaselineAsync` or `Case.CandidateAsync` consumer for over 99.9%
of its approximately 30-second active-stack timeline. The denominator is that
thread's reconstructed stack time, **not precise on-CPU time**, and shares are
not comparable elapsed-time ratios or confidence intervals.

| Transport / Side | Reading Thread | Binding Wrapper Inclusive | Reader Slow State Machine Inclusive |
|---|---:|---:|---:|
| Contiguous / Baseline | 3097 | 26.21% | 5.44% |
| Contiguous / Candidate | 3174 | 32.98% | 5.16% |
| Segmented128 / Baseline | 3270 | 16.03% | 42.82% |
| Segmented128 / Candidate | 3376 | 21.16% | 38.61% |

For candidate contiguous input, the record enumerator and binding wrapper had
27.12% and 24.96% exclusive shares; `ScanCore` had 5.07% inclusive share. These
are useful areas to investigate, not isolated instruction costs: inlined code
is attributed to callers, and the consumer also includes checksum work.
Segmented input has a substantially larger reader slow-path share, but this
does not isolate copying from scanning or async bookkeeping.

Stream4096 is inconclusive for CPU hotspot selection. The reading threads
(baseline 3511, candidate 3587) attributed 74.19% / 62.17% exclusive stack time
to `Monitor.Enter_Slowpath`; waits and runtime polling contaminate the timeline.
Do not conclude that those locks consume equivalent CPU or that stream binding
is cheap. Native/kernel CPU attribution remains unmeasured by this diagnostic.

### Independent Tier-1 JIT Evidence

The separate contiguous JIT processes retained normal tiering and PGO and did

|---|---:|---:|

an experiment unless correctness, controls and repeated timing improvement all
